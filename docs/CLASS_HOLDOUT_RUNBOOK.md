# CIFAR-100 class-holdout training runbook

This is operational control for the frozen protocol in `CIFAR100_CLASS_HOLDOUT.md`; it does not change the class partition, model, optimizer, checkpoint rule, detector, or evaluation population. The protocol and partition were declared and independently audited before training. The official CIFAR-100 test file was first read only after the class/validation partition audit; its 8,000/2,000 original-row population was independently audited without model scores.

## GPU contention guard, recorded before first successful launch

The sequential controller checks three `nvidia-smi` samples spaced two seconds apart before every seed. Each must have at most 4,096 MiB used VRAM, 55% total utilization, 10% memory utilization, and 55 W power draw. It runs at most one project GPU trainer at a time under a Windows file lock. A failed guard records `training_deferred_gpu_busy` and starts no trainer.

The first two controller attempts used a 45 W power ceiling and safely deferred at about 2.3 GiB VRAM, 35–45% utilization, 4–5% memory utilization, and 44–52 W. No class-holdout trainer, checkpoint, or OOD score was produced. Windows process inspection found no OOD Python process or game; desktop and browser graphics accounted for background GPU activity. The 45 W ceiling was therefore too sensitive to ordinary WDDM graphics power fluctuation. Only the operational power ceiling was increased to 55 W; the other three ceilings, sample count and spacing were retained. A read-only three-sample check after this amendment passed at about 2.3 GiB VRAM, 36–42% total utilization, 5% memory utilization, and 44–47 W.

The first successful `training-launch.json` records the controller/trainer/protocol/partition hashes and guard values. Later resumes must match those hashes. Preserve any failed seed folder and logs for review before retrying. A complete seed requires all 100 epochs, the first maximum of ID checkpoint-validation accuracy, a frozen selected checkpoint, and the independent training audit; partial seeds are not reportable.

## Evaluation execution boundary

Wait for all three 100-epoch seeds and the sequential trainer controller to finish before GPU extraction. Run `tools/audit_class_holdout_training.py` for every seed with `CUDA_VISIBLE_DEVICES=-1` in the verified CUDA Python environment. Seeds 0/1 also passed `tools/audit_class_holdout_checkpoint_inference.py` with CUDA hidden; it independently re-ran the selected checkpoint on only the 1,600-row ID checkpoint-validation role and saved raw logits. For seed 2, that strict CPU audit detected one extra correct prediction (1,254/1,600 CPU versus 1,253/1,600 recorded CUDA), so the original source and failed no-output attempt were preserved. A separate source-bound `tools/audit_class_holdout_checkpoint_cross_device.py` required a fresh three-sample GPU-idle guard, reproduced exactly 1,253/1,600 on the original CUDA inference path, identified only original training row 23,164 as a CPU/CUDA prediction disagreement, and saved both raw validation-logit arrays. This is an ID-only numerical audit exception, not a change to checkpoint selection, test labels, detectors or thresholds. Extract only after all three independent training and inference audits pass. Use the verified CUDA Python for `tools/extract_class_holdout.py`, one seed at a time under a fresh low-load GPU check. Use base Anaconda Python (which has SciPy and scikit-learn) for `tools/audit_class_holdout_features.py`, `tools/score_class_holdout.py`, and `tools/audit_class_holdout_scores.py`; the CUDA Python environment does not provide SciPy. The scorer requires the independently audited ID feature fit before it will run. Preserve any partial extraction/scoring folder for review; the scripts refuse to overwrite it. No class-holdout OOD score or metric exists yet.

Seeds 0/1 also completed the strict CUDA-hidden `tools/audit_class_holdout_checkpoint_inference.py`; seed 2 instead completed the documented `tools/audit_class_holdout_checkpoint_cross_device.py` with a fresh internal GPU guard, saving both raw ID-validation paths. Preserve every existing audit directory; never overwrite it.
2. For N=0,1,2 sequentially, run `tools/extract_class_holdout.py --seed N` in the verified CUDA Python. The script itself checks all three completed schedules and both audits per seed, then requires three two-second-spaced samples under <=4,096 MiB VRAM, <=55% GPU, <=10% memory utilization and <=55 W before any extraction output is created. A busy-GPU deferral leaves no extraction folder; wait for a later quiet window. Never launch a second extraction/trainer concurrently.
3. After each complete extraction, run `tools/audit_class_holdout_features.py --seed N`, `tools/score_class_holdout.py --seed N`, and `tools/audit_class_holdout_scores.py --seed N`, in that order using base `C:\Users\zxzx\anaconda3\python.exe` with SciPy/scikit-learn. Scoring requires the passed feature-fit audit. Each stage refuses to overwrite an existing output; inspect/preserve a partial folder before any recovery.
4. Only after all three per-seed score audits pass, run `tools/build_class_holdout_summary.py` then `tools/audit_class_holdout_summary.py` in base Python. The summary prints every fixed method and temperature variant with per-seed points and sample SD; it must not name a test-selected winner. Then run the project 91-test CUDA-hidden regression, save the full passing output as `report/cifar100-class-holdout/regression.log`, and run `tools/verify_class_holdout_completion.py --write` in base Anaconda Python. The write-once gate hashes all three selected/full checkpoints, raw extracted/scored arrays, frozen declarations, independent audits, report and code sources; rerun the verifier without `--write` for read-only verification before treating the report as complete.
